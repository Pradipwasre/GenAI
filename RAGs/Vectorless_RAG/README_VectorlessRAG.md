## What Is Vectorless RAG

Retrieval-Augmented Generation (RAG) is a technique where a language model answers questions by first retrieving relevant text from a document, rather than relying solely on its training data.

Traditional RAG does this by splitting the document into small text chunks, converting each chunk into a vector using an embedding model, and storing those vectors in a vector database. At query time, the query is also embedded and the closest chunk vectors are retrieved using cosine similarity.

Vectorless RAG removes the embedding step entirely. Instead of vectors, the document is organized as a tree of nodes, where each node carries a short text summary. When a question is asked, the LLM reads these summaries and navigates down the tree to find the most relevant page. There is no vector database, no embedding model, and no similarity score computation. The entire retrieval is driven by the LLM reading and reasoning over summaries.

This approach is particularly well-suited for structured documents such as annual reports, legal filings, research papers, and manuals, where the content has a natural hierarchy of sections and pages.

---

## How the PDF Data Is Stored

The document is not stored as flat chunks. It is organized as a three-level hierarchical tree.

**Level 2: Leaf Nodes (Page Nodes)**

One node is created for each page of the PDF. Each leaf node stores the full raw text of that page, a short LLM-generated summary of that page (2 to 3 sentences), the page number as a range tuple, a unique node ID such as `page_1`, and a reference to its parent section node.

**Level 1: Section Nodes**

Every five consecutive pages are grouped into one section node. The section node stores the combined raw text of all five pages, a summary generated by the LLM from the five individual page summaries, the page range it covers such as pages 1 to 5, child links to its five leaf nodes, and a reference to the root node.

**Level 0: Root Node**

There is a single root node at the top. It stores a high-level summary generated from all section summaries, the full page range of the document, and child links to all section nodes.

The resulting structure looks like this:

```
root (level 0)
  summary: high-level overview of the whole document
  |
  section_1 (level 1, pages 1-5)
    summary: overview of pages 1-5
    |
    page_1 (level 2) -- raw text + page summary
    page_2 (level 2) -- raw text + page summary
    page_3 (level 2) -- raw text + page summary
    page_4 (level 2) -- raw text + page summary
    page_5 (level 2) -- raw text + page summary
  |
  section_2 (level 1, pages 6-10)
    ...
```

Each node is an instance of the `DocumentNode` dataclass, which holds the fields: `node_id`, `level`, `page_range`, `raw_text`, `summary`, `children`, and `parent`.

## How the LLM Helps

The LLM (GPT-4o-mini in this notebook) is involved at two distinct stages:

**Stage 1: Index Construction**

During index building, the LLM is called to summarize each page individually and then each section as a group. The prompt instructs the model to be specific about numbers, section names, and key facts, and to keep the summary to 2 to 3 sentences. These summaries are stored permanently inside the nodes and are the only information used later during retrieval navigation.

**Stage 2: Query-Time Traversal and Answering**

When a query arrives, the LLM is used twice for navigation and once for answering.

In the first navigation call, the LLM is shown all section summaries and asked to return the index number of the most relevant section for the query. The model replies with a single integer.

In the second navigation call, the LLM is shown all page summaries within the chosen section and again asked to return the index of the most relevant page.

In the final answer call, the LLM is given the raw text of the selected page and asked to answer the question from that content.

This means the LLM is acting as the retriever, not just the reader. It replaces cosine similarity with language-level reasoning over summaries.

---

## How Context Is Retrieved

Retrieval follows a top-down tree traversal with three steps.

**Step 1: Section Selection**

The query is sent to the LLM along with all section node summaries. The LLM returns the index of the most relevant section. For example, for a query about dividend declarations, the model would select the section whose summary mentions shareholder distributions.

**Step 2: Page Selection**

Within the chosen section, the query is sent again along with all page summaries from that section only. The LLM returns the index of the most relevant page. This narrows retrieval from a section of five pages down to a single page.

**Step 3: Answer Generation**

The raw text of the selected page is passed to the LLM as context, along with the original question. The model reads the actual document text and generates the final answer.

The key distinction from traditional RAG is that the model is navigating through the index using summaries, never computing a similarity score between the query and every chunk. The traversal is deterministic and explainable: you can trace exactly which section and page were selected and why.

## Code Structure

The notebook is organized into ten sections.

**Section 1: Background**

Covers the conceptual difference between Traditional RAG (chunk, embed, retrieve by similarity), Vectorless RAG (summarize, store as tree, retrieve by LLM traversal), and Hybrid RAG (combine both). Includes a comparison table across storage type, retrieval method, scalability, and suitability.

**Section 2: Setup and Installation**

Installs `pypdf`, `llama-index`, and `openai`. Imports standard libraries (`os`, `requests`, `pathlib`, `dataclasses`, `typing`) and sets the OpenAI API key.

**Section 3: Load the Financial Report PDF**

Downloads the BSE annual report PDF from a public URL using `requests`. Extracts page text using `PdfReader` from `pypdf`. Stores all page texts as a plain Python list called `pages`.

**Section 4: Building the Hierarchical Index**

Contains four sub-cells.

`DocumentNode` dataclass: defines the node structure with fields for id, level, page range, raw text, summary, children, and parent.

`summarise()` function: sends a text excerpt to the LLM and returns a 2 to 3 sentence summary. Used during index construction for both pages and sections.

`build_index()` function: iterates over pages to create leaf nodes, groups them into section nodes, and creates the root node. Each node's summary is generated by calling `summarise()`.

`print_tree()` function: a utility to recursively print the full tree structure with indented summaries, useful for inspection.

**Section 5: Querying the Hierarchical Index**

Contains two functions.

`select_best_child()`: takes a query and a list of nodes, formats their summaries into a numbered prompt, asks the LLM to return the best index, and returns the corresponding node. Includes input validation to prevent index out-of-bounds errors.

`vectorless_query()`: the main retrieval function. Calls `select_best_child()` twice (once for section, once for page), then sends the raw page text to the LLM for the final answer. Logs each step to the console.

**Section 6: Sample Queries**

Runs four representative queries against the annual report: total revenue, board of directors, dividend declaration, and auditor observations. Each query result is printed to demonstrate the retrieval pipeline end to end.

**Section 7: Traditional RAG Baseline**

Implements a minimal TF-IDF based retrieval pipeline for comparison. `build_traditional_index()` splits page text into 300-word chunks and fits a `TfidfVectorizer`. `traditional_query()` transforms the query using the same vectorizer, computes cosine similarity against all chunk vectors, retrieves the top-2 chunks, and sends them to the LLM for answering.

**Section 8: Side-by-Side Comparison**

Runs the same revenue query through both systems and prints the answers together. This section exists to let students observe practical differences in the two retrieval paths.

**Section 9: Summary and Key Takeaways**

A comparison table covering index type, retrieval logic, strengths, and limitations for both approaches. Recommends Hybrid RAG as the production default.

**Section 10: Exercises**

Four hands-on tasks: varying section size to observe accuracy changes, replacing TF-IDF with dense embeddings, adding a confidence score to enable fallback to vector search, and extending the tree to four levels.
